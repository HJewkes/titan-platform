# active-work

**Product.** Published to npm as `@titan-design/active-work`. Depends on
[`agent-protocol`](/reference/agent-protocol), [`cluster`](/reference/cluster),
[`daemon`](/reference/daemon), [`decider`](/reference/decider),
[`locator`](/reference/locator), [`pm`](/reference/pm), [`registry`](/reference/registry),
[`retrieval`](/reference/retrieval), [`session-analytics`](/reference/session-analytics),
[`session-graph`](/reference/session-graph), [`session-read`](/reference/session-read) and
[`store-sqlite`](/reference/store-sqlite).

```sh
npm install -g @titan-design/active-work
active-work setup
```

## The problem it solves

Engineering work spans days; Claude Code sessions do not, and every handoff between
sessions, machines or agents loses context unless something durable holds it. active-work
keeps a small set of plain markdown and YAML files per initiative and exposes them through
one command registry, so the CLI, the MCP server, the loopback daemon and the skill all read
and write the same source of truth.

## When to reach for it

- You want `aw <slug>` to start a session in the initiative's worktree with its bootstrap
  prompt: brief excerpt, open tasks, open loops, artifacts and the last session.
- You want to add, edit or finish tasks, record notes and sources, or track branches and
  pull requests against an initiative, from a shell or from MCP tool calls.
- Another product needs initiative state. Call the CLI or MCP; products never import each
  other. For the task schema alone, use [`pm`](/reference/pm).

## Example

Verified against 0.23.0.

```sh
active-work new demo-initiative --title "Demo initiative"
active-work task add demo-initiative --title "Write the first draft"
aw demo-initiative
```

## What it deliberately does not do

It does not own task semantics shared with other products; those live in `pm`. It never
writes outside its data root and `~/.claude`, and it does not sync between machines.

## Gotchas

- `ACTIVE_ROOT` is the only safe override of the data root. `XDG_DATA_HOME` is ignored on
  macOS.
- `postinstall` copies the skill into `~/.claude` only from an installed copy under
  `node_modules`; a workspace `pnpm install` leaves it alone.
- `docs/cli-reference.md` is generated by `prepack`, so it is in the tarball but not in git.
