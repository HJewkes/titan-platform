A stacked PR whose fix-proof judged its parent branch no longer merges into main on that read after GitHub retargets it with the same head (TP-4259). A merge decided on a base passes Shepherd's merge guard only on positive proof there: the MERGE's `proofBase` is that base, or a fix-proof read taken on that base (step `sh-fix-proof:<head>@<base>`, through the review's own read and judge) is a clean line naming it, a proved CI read for a workflow-only diff naming it, a believed missing run, a kind that needs no proof, or the owner waived the proof at the head. A record, line or read with no base proves nothing. A fix-proof run binds only through a line naming the base it judged, so a judge's line from before that field never binds and the read ends in an error at its deadline. Off the decided base, an allow or a mechanical MRG-AU gate becomes a `shepherd-merge-guard/no-facts` gate that no coordinator may resolve; any other gate keeps its own rule, with the off-base proof named first. A registration store, registration or head branch that cannot be read now makes the fix-proof read an `error`, not `skipped`. A skipped fix-proof judge never counts as a run. fix-proof.yml now also runs on an `edited` event that changes the base, so the retarget starts a run on main; any other edit skips every job in a concurrency group of its own, so it cancels nothing.
