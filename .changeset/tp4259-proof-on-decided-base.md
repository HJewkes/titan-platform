A stacked PR whose fix-proof was bound to its parent branch no longer merges into main on that read after GitHub retargets it with the same head (TP-4259). Every fix-proof read that gets a binding now records the base it looked for (`boundBase`), whatever its trust, and the MERGE records it as `proofBase`. Shepherd's merge guard fires only when `proofBase` names another base than the one being decided; a record with none (a kind that needs no proof, a read that got no binding) is governed by owner decision 303 as before, and 303 is unchanged for every PR on its own base. When the guard fires, land reads the head's fix-proof again on the decided base through the review's own `sh-fix-proof` read (step `sh-fix-proof:<head>@<base>`) before deciding. It merges once a line or CI read names that base, whose trust is judged by 303; a skipped read, a missing run looked for there, or the owner's waiver also clear it. The one new owner gate is a re-read after a retarget that names no run on the new base, or another base's, or reads NO_REPRO. A fix-proof run binds only through a line naming the base it judged. Off the decided base, an allow or a mechanical MRG-AU gate becomes a `shepherd-merge-guard/no-facts` gate; any other gate keeps its own rule, with the off-base proof named first. A registration store, registration or head branch that cannot be read makes the fix-proof read an `error`, not `skipped`. A skipped fix-proof judge never counts as a run. fix-proof.yml also runs on an `edited` event that changes the base, so the retarget starts a run on main; any other edit skips every job in a concurrency group of its own.
