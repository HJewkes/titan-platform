A stacked PR whose fix-proof was refused on its parent base no longer merges into main on that refusal after GitHub retargets it with the same head (TP-4259). Both fix-proof reads now share one run selector that never counts a run whose line is the stacked-base refusal, so a first read after the retarget judges the run against main alone, and a refused line stays the head's standing instead of hiding under an untrusted reason. Before deciding a merge into the default branch a refused standing names, Shepherd reads the head's fix-proof again (`sh-fix-proof-rebound`) through that same reader, waiting past the refused run, and judges the line by the first read's rules: a NO_REPRO, error, untrusted or unread read leaves it unproven. Until a read stands, the allow is a `no-facts` gate that asks the owner. fix-proof.yml also runs on a base edit, so the retarget starts that run, and a skipped judge from any other edit is no longer read as a fix-proof run. A refused or errored proof's own message now appears in the MERGE's recorded fix-proof standing.
