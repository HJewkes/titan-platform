# deploy/hub: the shared Matrix hub

The Matrix homeserver every area uses to reach the owner's phone: Tuwunel behind Caddy, with
federation off and public registration closed. It was ported unchanged from the TP-301 spike
(`~/projects/spikes/tp301-matrix-substrate` at `fb8413e`); the evidence behind each setting is
in that spike's `RESULTS.md`.

**Stage 1 runs Tuwunel and Caddy only.** The `core` service (broker-core, `src/core.mjs`, built
from `core.Dockerfile`) exists for stage 2 and is not started: it sits under the compose profile
`core`, so neither command below brings it up. Its appservice registration is still rendered, so
Tuwunel knows the `@core-.*` and `#coord.*` namespaces even though nothing uses them yet;
`src/bootstrap.mjs` only creates the owner's `#queue`, over the edge1 mirror user.

## Layout

- `scripts/setup.sh` fills missing `.env` keys once (tokens from `openssl rand -hex 32`), then
  renders `config/tuwunel.toml.tmpl` and `appservices/*.yaml.tmpl` into the gitignored `data/run`.
  `SERVER_NAME` (default `tp301.local`) is the only place the server name lives. Setting
  `PUBLIC_BASE_URL` also appends `config/tuwunel.remote.toml.tmpl` (`ip_source`, online backups,
  client well-known). `.env.example` lists every key it writes.
- `docker-compose.yml`: `tuwunel` on `127.0.0.1:8008`, `caddy` under the profile `remote`, `core`
  under the profile `core`, and a commented `mautrix-telegram` block (not used in stage 1).
- `config/caddy/Caddyfile`: TLS for `SERVER_NAME`; proxies `/_matrix/*`, `/_tuwunel/*` and
  `/.well-known/matrix/client`.
- `src/lib.mjs`, `src/bootstrap.mjs`: owner-side scripts over `@titan-design/matrix-bus`.
  `src/core.mjs` is the stage-2 core service and stays on `matrix-js-sdk`. `pnpm install` at the
  repo root installs their dependencies.

## Local run

Needs Docker, plus Node 22 for the owner-side scripts.

    ./scripts/setup.sh
    docker compose up -d --build
    curl localhost:8008/_matrix/client/versions
    pnpm run bootstrap   # owner account, the ac-edge1 mirror user and #queue

## Remote run

On a fresh VPS with an empty `data/`. The VPS needs Docker alone.

    printf 'SERVER_NAME=chat.example.org\nPUBLIC_BASE_URL=https://chat.example.org\n' > .env
    ./scripts/setup.sh && chmod 600 .env
    docker compose run --rm tuwunel --execute "users create_user owner"   # note the password, then Ctrl-C
    docker compose --profile remote up -d --build

The last line starts Tuwunel and Caddy. The compose sets `TUWUNEL_CONFIG`, so no `--config` flag
is needed, and the image's built-in health check finds the config.

**The server name cannot change once `data/db` exists.** Tuwunel bakes it into every id.
`setup.sh` records it in `data/server_name` and refuses a different one with
`data/db was created for <old>, not <new>; wipe data/db or restore SERVER_NAME` (exit 1). Start
the VPS with an empty `data/db`, and never copy a laptop's `data/` to it.

## Backup

With `PUBLIC_BASE_URL` set, Tuwunel writes online database backups to `data/backup`
(`database_backup_path`) and keeps the latest 3 (`database_backups_to_keep`). Back up
`data/backup`, `.env` (it holds every token and the owner password) and `data/caddy/data`
(certificates). `data/run` is regenerated by `setup.sh` from `.env` and the templates. A restore
must keep the same `SERVER_NAME`.

## Upgrade

The compose tracks `ghcr.io/matrix-construct/tuwunel:latest`; the spike verified Tuwunel 1.9.2
(`sha256:a354976db35cb6e3f8c0b801f266592571af898554d78fc6e2137f14e02a7d3e`). To upgrade, take a
backup, then `docker compose pull` and `docker compose --profile remote up -d`. The compose sets a
30-minute `stop_grace_period` for Tuwunel; let a stop finish rather than killing the container. After a
template change, re-run `./scripts/setup.sh` (it keeps existing `.env` keys) and restart Tuwunel.
